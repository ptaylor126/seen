**Decisions worth remembering**

- **Deepening `bg` alone to separate white surfaces is NOT viable — it collapses the `bg ↔ surfaceAlt` gap and flattens the recessed filter zone.** The naive fix (just darken `bg`) lands `bg` at ~81 luminance, which is exactly where `surfaceAlt #ECE8E1` already sat (81.0) — so `bg→surfaceAlt` contrast drops to ~1.00 and the Library/Friends filter-zone wash (and several modal footers) visually vanishes. **Decisions worth remembering**

- **`ON CONFLICT DO NOTHING` on an upsert meant to "keep this row current" is a latent bug** — bad or partial rows become permanent and silently no-op every future write. Today's failure: stub rows in `public.titles` (title / poster_path / backdrop_path NULL, traced to a 2026-06-09 backfill TMDB-hiccup that slipped past the `if (!res.ok)` guard and inserted with all-null fields) were skipped by every subsequent forward-path `ensure_title` call because of the DO NOTHING. UI surfaced "Unable to load title" on a row that had clearly been touched. Fix: `DO UPDATE SET col = COALESCE(excluded.col, titles.col)` — stubs heal on the next write, and the `coalesce` prevents a future caller's accidental NULL from clobbering an existing populated field. **Generalises**: any `ensure_*` / "stamp the catalogue with fresh source-of-truth data" pattern should be DO UPDATE COALESCE, not DO NOTHING. Reserve DO NOTHING for cases where the upsert is genuinely "first write wins, ignore subsequent attempts" (idempotent inserts of immutable events). The stub source itself — `if (!res.ok)` not catching 200-with-error-body — is a worth a separate look in any TMDB script.

- **The `p_*` parameter rename finally eliminated the `#variable_conflict use_variable` trap that bit `ensure_title` repeatedly.** Same function, same shape: parameter names matching column names + `use_variable` → plpgsql substituted parameter placeholders into column-reference positions where it shouldn't. 2026-06-10 hit the ON CONFLICT col_list (fixed with `ON CONFLICT ON CONSTRAINT titles_pkey`). 2026-06-16 hit the DO UPDATE SET LHS (no constraint-name shortcut exists for that position). Both bugs were the same root cause; only the position differed. The 2026-06-10 fix migration noted the rename was rejected as "no functional advantage over the constraint-name reference" — that judgement was correct at the time (just ON CONFLICT) but wrong as soon as the function grew DO UPDATE, which the original design didn't anticipate. **Rule going forward**: every new RPC parameter gets a `p_` prefix at write time, no exceptions. Then `use_variable` is unnecessary (default `use_column` works in every parser position) and the trap is structurally impossible to reintroduce. The constraint-name shortcut was a band-aid for one position only; the rename is the structural fix.

- **Search-field dismissal: two-affordance pattern.** X (inline, inside the field) = clear-but-stay (clear query, keep focus + keyboard up). Cancel (outside the field, on focus) = full exit (blur + clear + dismiss keyboard). Apply consistently across every search surface that has both a focused-while-empty and a typing state. Today's fix: Library local-filter mode had only inline X (which couldn't help when the field was focused-but-empty), and friend's-library had neither inline X nor Cancel — both surfaces stranded the user with no obvious way to dismiss the keyboard except the device return key. Generalises: any search that supports focus-without-text needs both affordances; a text-only "+/X toggle" or single trailing slot is not enough. The shared `SearchBarInput` (Home) already had this pattern via `overlayVisible` driving Cancel; the two local-filter surfaces needed their own focus state because they're custom TextInputs that don't go through `useSearchBar`. Pattern is now consistent across all four search surfaces.

- **`DEFERRABLE` UNIQUE constraints cannot be `ON CONFLICT` arbiters in Postgres — you can't have both.** Verified live today by reproducing the favorites rank-swap collision: a non-deferrable UNIQUE is checked per-row during multi-row UPDATEs (the unique INDEX is updated row-by-row, so a transient duplicate trips it mid-statement), which makes any atomic rank-swap impossible in one statement. `DEFERRABLE INITIALLY DEFERRED` moves the check to transaction commit and the rewrite passes through the duplicate state cleanly — BUT once the constraint is `DEFERRABLE`, supabase-js `.upsert({ onConflict: 'col,col' })` against it fails with 42P10 "no unique or exclusion constraint matching the ON CONFLICT specification" (PG docs explicitly disallow deferrable uniques as arbiters). The decision is forced: (a) keep non-deferrable + use DELETE+INSERT for multi-row updates and accept the race window, or (b) go DEFERRABLE + rewrite the dependent UPSERT as SELECT-then-INSERT-or-UPDATE (two round-trips, race window often unobservable depending on the surface). The favorites editor took (b) because reorder is the primary action there and the single-user race is unobservable. Generalises to any "swap unique values within one row set" pattern — going in, decide which UPSERT call sites depend on that constraint as an arbiter, because they'll all need rewriting.

**Decisions worth remembering**

- **`service_role` REST surface needs to be audited per Edge Function, not per table**: the project-level lockdown posture (every public table at `Dxtm/postgres` — no DML for service_role by default) means every Edge Function that reads or writes via `service_role` needs a scoped grant migration covering exactly the tables and operations it touches. We hit this twice on push (push_tokens, then profiles + 2 more) and it cost a debugging round each time because the audit wasn't done upfront. Pattern for future Edge Functions: before deploying, grep `supabase.from(...)` plus `.select|.insert|.update|.delete` across the function's source, then write a single scoped-grant migration covering everything. The `20260609120000` / `20260609140000` / `20260610100000` comment blocks set the template.

- **Edge Functions that silently skip on data-resolution failure should at minimum log a warn before returning the "skip" response**: `send-push-notification`'s `buildMessage()` returns `null` from many gates (missing payload field, missing helper-fetched name, missing TMDB title, etc.), all of which the top-level handler collapses into `200 message_skipped: true`. That ambiguity cost the second debugging round. The helper functions DO log warns on most failure paths (`TMDB_ACCESS_TOKEN missing`, `profile fetch failed`, etc.) but not all — `fetchDisplayName` returns null silently when `display_name` is empty/null, for example. Future Edge Functions: every return-null gate that the caller treats as a skip should log a warn naming which gate fired and what input data was missing. The cost is a few extra log lines in the common path; the benefit is that future debugging reads the logs instead of running elimination experiments.

- **Per-install `device_id` + reap-on-`DeviceNotRegistered` doesn't clean up duplicates on the common iOS case** (reinstall → same Expo token reissued → reap never fires because Expo keeps the old token "valid"). Set-on-value dedup at send time is the structural fix and covers any future row accumulation regardless of cause — the reap path now only matters for genuine token invalidation (app uninstalled, never reinstalled). The `src/lib/push.ts` header comment was updated in this batch to say so explicitly.

- **`#variable_conflict use_variable` substitutes parameter names into EVERY identifier position in the function's SQL, not just expressions** — including `ON CONFLICT (col_list)` targets, which look syntactic but are processed by plpgsql's binder first. If parameter names overlap target-table column names AND the function needs an ON CONFLICT clause, use `ON CONFLICT ON CONSTRAINT <name>` instead (constraint names aren't substituted). Either that, or rename parameters to avoid the conflict and drop `use_variable` entirely. Companion observation to today's other Decision on Edge Function silent skips: same shape, different layer — a `void`-wrapped client helper around an erroring RPC let a structural bug live for the lifetime of a feature (stage 3 ship → today). Silent error sinks on optional / best-effort paths hide bugs that present as "feature was never working."

- **When two surfaces show the same domain fact in different shapes, pair the formatters in one module so they can't drift.** Today's example: inbox rec card shows `"Watched · 4★"` (compact list-row badge); title-screen YOUR marker shows `"You rated this 4★"` (full sentence). Same fact, two display contexts. Putting both `formatYourMarker` and `formatLibraryBadge` in `src/lib/item-status.ts` (with the shared `ItemStatus` type) means a wording change on one side requires a deliberate edit to the matching function in the same file — no chance of one surface saying "Watched" while the other says "Already seen." Generalises: any time a domain fact appears in two visual shapes (full-vs-compact, badge-vs-sentence, list-row-vs-detail), keep the formatters adjacent and the type definition with them. Cheaper than a feature-test for cross-surface consistency, and the diff makes the relationship obvious to future readers.

- **`FunctionsFetchError` is the only retryable error class in `@supabase/functions-js`** — it's the transport-layer fetch rejection (network blip, DNS hiccup, cold-start socket timeout) where retrying often resolves silently. Discriminator: `error.name === 'FunctionsFetchError'`, NOT `error.context instanceof Response` sniffing (the constructor sets the name string deliberately for this kind of branching). `FunctionsHttpError` (4xx/5xx response) is a conscious server reply and skips retry — auth issues, malformed requests, function code errors are real failures that blind retry masks. `FunctionsRelayError` similarly indicates infrastructure misrouting and isn't transient in the retry-friendly sense. Retry once at ~700ms, never exponentially — bounds worst-case latency to a single back-off and avoids hammering when an endpoint is genuinely down. Pattern lives in `src/lib/tmdb.ts > callProxy`; reusable shape for any other Edge-Function-calling wrapper we add (`delete_account`, future RPC wrappers).

- **Layer error UX in two places: silent retry at the wrapper, friendly surfacing at the consumer.** `callProxy` handles the "fetch didn't complete, try once more" reality of mobile networks invisibly. Consumers (`OnboardingSearch`, title screen, etc.) only see a thrown error when BOTH attempts failed — a persistent issue worth telling the user about. Crucially, the consumer doesn't need to know whether the failure was transient — that's already been resolved one layer down. So the consumer's "this failed" path only fires on genuine persistent failure, and only there does it need user-friendly wording + a retry affordance. Narrow responsibilities each: the wrapper knows about networks, the consumer knows about UX context. Companion to today's `service_role` audit-per-Edge-Function decision: in both cases the principle is **handle the structural concern as close to its source as possible** rather than pushing it up to every call site.

**Decisions worth remembering**

- **Shared catalogue table > denormalising onto user rows for TMDB-sourced metadata**: stage 1 added five metadata columns to `items` and got reverted before any data wrote. The pivot was correct — a popular title lives in dozens of users' libraries, so stamping per-row meant the same TMDB metadata duplicated N times AND every insert site had to know the columns. `public.titles` keyed on `(tmdb_id, media_type)` solves both: one row per real-world title, items join via the pair they already carry, refresh-from-TMDB is one UPDATE not N. The pattern applies to any future TMDB-sourced surface — credits, watch_providers, images — if we ever need to cache them.
- **`service_role`'s "no DML on `public.*`" posture is deliberate-by-accident and worth preserving**: the absence of `GRANT ALL TO service_role` in this project's migrations means a leaked service-role key cannot reach user data via the REST API — the GRANT layer rejects every DML attempt before RLS-bypass even matters. The 2026-06-09 grant deliberately opens only the two-table, three-operation sliver the titles backfill needs. **Future service_role work** (`delete_account` Edge Function, any cleanup job) should follow the same scoped-grant pattern — add what that job needs to the specific tables it touches, **never restore schema-wide service_role access via `GRANT ALL` or `ALTER DEFAULT PRIVILEGES`**. The locked-down posture is the security property; widening it once defeats it everywhere.
- **rls-auditor agent post-create-migration catches the two-layer mistake reliably**: writing a SELECT policy without the matching table-level GRANT means the policy never evaluates — every client read fails at 42501 before RLS runs. The auditor flagged this on `titles` while I was focused on the new-table content, and a companion grant migration (`20260609111000`) shipped before any client tried to read. Pattern: **always run rls-auditor after any migration that adds/alters/drops policies, and treat its FAIL as a re-approval gate** (per the in-memory rule), not a rubber stamp.
- **A perf migration can earn the data foundation for parked product features as a side effect, and that's worth noticing**: the four-stage metadata arc was scoped to fix the library spinner, but it also built two surfaces that were previously schema-blocked. `titles.genre_ids` is GIN-indexed and now loaded onto LibraryRow on every fetch, so the genre filter is a pure UI task. `titles.original_language` (ISO 639-1) is loaded the same way, so language display (title detail, library row chip) is UI-only. The next time a perf job touches the data shape, look for these adjacent wins before scoping the migration.
- **`ensure_title` is intentionally callable for any title without an items-row check**: a client could in principle stamp an orphan titles row at a tmdb_id no items row references. `ON CONFLICT DO NOTHING` blocks overwrite of an existing row, and items has its own per-user RLS, so the orphan can't surface to other users — the vector is storage write-amplification, no read path back to anyone. Hardening deferred (could require the caller to have an items row at the same `(tmdb_id, media_type)`); the rls-auditor flagged it as informational, non-blocking. Worth noting so a future PR doesn't reflexively close it without weighing the added plumbing for a vector that can't actually hurt anyone.
- **A horizontal `ScrollView` next to a non-`flex: 1` `FlatList` in a column-flex parent will collapse on full content**: the FlatList sizes to its intrinsic content height; on a full tab the parent column-flex has to shrink siblings to fit, and the default `flexShrink: 1` makes the ScrollView the casualty — its contentContainer stays intrinsic-tall, its outer frame gets squeezed, chips clip. Fix is `flexShrink: 0` + an explicit `height` on the strip (either alone works; both together makes the intent obvious to future readers). General RN layout gotcha worth carrying — applies to any horizontal chip strip / tab bar / inline toolbar that sits next to a content list without `flex: 1`. Either give the strip explicit sizing, or give the list `flex: 1` and let the strip take its natural height.
- **For a toggleable filter UI, push the active-state signal onto the trigger affordance, not the revealable surface**: the Genre toggle pill carries the active-filter signal on its own (accent fill + selected genre name), so the chip strip below doesn't need to be visible for the user to see they're filtering. Collapsed-with-active-filter is a fully legible state — the strip is purely a "change the selection" affordance, not part of the active-filter feedback loop. Saves vertical real estate without sacrificing clarity. Same pattern fits any reveal-on-tap filter where the active value can fit on the trigger.
- **Extract reusable logic (and only reusable logic) once a second screen needs it — the boundary is logic + presentation shared, data loading screen-local**: the friend-library parity work landed cleanly because the four controls' state and filtering ARE identical between the two screens (post-stage-4, both row types satisfy `FilterableLibraryRow`), while the loaders and renderers genuinely DIFFER (RLS scopes, recommendation-attribution join, add-overlay). Extracting hooks + presentation while letting each screen own its loader and renderer means future library-style screens (public profile, discover, any TMDB-shaped row list) inherit the four controls for free — same payoff pattern as the earlier `ViewControls` extraction. The trap to avoid is the reverse: had we tried to share the loader too (a generic `useLibrarySource(...)` parameterised by RLS scope + joins), the param surface would have ballooned to express the differences and we'd have ended up with a worse copy.

- **One visibility column governs the whole library item, not per-feature flags**: `items.visibility` (text enum) is the single source of truth for "who can see this title's library footprint" — covers ratings, watched-state, reviews, and any future friend-activity surface tied to a watched item. - **Delegate downstream RLS to the source table via EXISTS rather than re-implementing the rule**: the reviews SELECT policy asks "is the parent items row visible to me?" by checking items's own RLS through an EXISTS subquery. The visibility helper lives in one place; future visibility changes (e.g. a `'public'` tier) land in `is_item_visible_to_auth` and propagate everywhere automatically.
- **Content-attribute vs. visibility-setting is a distinction worth keeping**: `contains_spoilers` is a content-attribute — travels with the row, no RLS gate, no separate column on the parent table. Anyone who can already SELECT the row sees the flag; honoring it is a client decision. Saves a column and a policy versus mishandling it as a visibility variant.
- **For modals with a text field + commit action, put the commit button in the header from the start**: both the review modal and the recommend modal started with the commit button (Save / Send) pinned in the bottom bar, and both turned out to be partially-hidden-behind-the-keyboard despite KAV — once on the review modal (tall body field), and again on the recommend modal (multi-line note that grew as the user typed). Pinned-bottom inputs are fine; pinned-bottom **commit buttons** are a trap when the input next to them can grow.
- **Direct keyboard-height lift > KeyboardAvoidingView for pinned-bottom inputs that can grow**: KAV's `behavior='padding'` + `keyboardVerticalOffset` indirection is brittle when a pinned input grows (multiline TextInput) — the calculation doesn't always land the bar fully above the keyboard. Pair with a `maxHeight` on the input so the bar's growth is bounded. The recommend modal uses this pattern; the review modal doesn't need it because its body field is the scroll surface, not a pinned bar.
- **Tap-anywhere-outside-text-field dismisses keyboard via `Pressable` + `Keyboard.dismiss()`**: cleaner than ScrollView's `keyboardShouldPersistTaps` tricks. Wrap the non-bottom-bar body area in a Pressable; TextInput captures its own touches first (typing keeps the keyboard up); taps on background View elements bubble to the Pressable and dismiss. **Decisions worth remembering**
- **Recipient-only vs. party-only is per-table, not per-feature**: rec-level reactions are recipient-only (signal flows one way: from the person who received the rec); comment reactions are party-only (conversation flows both ways). Same shape of helper (`is_recipient_of_rec` vs. `is_party_to_comment`), opposite scope. Don't reflexively apply one model to the layer below.
- **Per-policy data cleanup belongs IN the same migration**: when an RLS write policy tightens, any rows previously written that would no longer be writeable by their author should be purged in the SAME migration (or grandfathered with an explicit delete-only legacy policy). Otherwise you get stuck rows: SELECT-visible to all, un-DELETE-able by the author, misrepresenting the new rule. The recipient-only rec-reactions migration purged 1 production row; future tightenings should follow the pattern.
- **Long-press popover anchoring via `e.nativeEvent.pageY`**: avoids the per-element `useRef` + `measureInWindow` dance for the lean version. Touch-position-based anchoring is functionally fine when the popover is centered horizontally and just below the touch — the finger area is already obscured anyway. Upgrade path to ref-based exact anchoring exists but isn't needed yet.
- **Sibling backdrop, not parent backdrop**: tap-outside dismiss works because the backdrop Pressable and the popover sheet are SIBLINGS in the Modal root, not nested. Nested would have inner Pressables bubble taps to the parent backdrop and dismiss on every interaction. Worth remembering for any future popover/overlay patterns.
- **Extensibility-aware structure beats refactor later**: the popover actions menu was built as an `Array<{label, destructive?, onPress}>` from day one even though it only had one item (Delete). Adding Edit later is now a one-line append instead of a re-architecting pass. Cheap to do up front; expensive to retrofit.

**Decisions worth remembering**

**Bug fixes & lessons**
- React state updates from `setState` (even with `await` inside an async function) don't propagate to other consuming components instantly — the consumer re-renders on the next React render after the setState lands. If the same callback ALSO schedules a navigation (e.g. `router.replace('/(tabs)')`), the routing/segments change can outpace the state propagation: the consumer renders with new segments but old state, triggering whatever the layout effect does in that combination. **Decision rule**: if the post-mutation flow involves both updating shared state AND navigating, let the consuming layout's effect own the navigation based on the new state. Manually calling navigate alongside refresh is a race the layout will lose half the time.
- React Native flex children default to `minHeight: 'auto'` (= content height), which means a `flex: 1` column won't shrink below its children's natural height — children spill past the parent's bounds. The fix is `minHeight: 0` on each flex node in the chain. If a `FlatList` is inside a `flex: 1` container that's inside another `flex: 1` container, every level needs `minHeight: 0` or the innermost list will refuse to shrink and will overflow into whatever sibling sits below.
- `KeyboardAvoidingView`'s `keyboardVerticalOffset` documentation describes it as "distance from screen top to KAV top", NOT "subtract from bottom". So passing `insets.bottom` (the home-indicator inset) to cancel a SafeAreaView's bottom edge does NOT work as you'd hope — empirically the gap to the keyboard was inconsistent across screens. The reliable pattern when you want the footer hugged to the keyboard is: drop the SafeAreaView's bottom edge (`edges={['top']}`), let KAV pad with the default offset (0), and manually add `insets.bottom` to the footer's `paddingBottom` only when the keyboard is closed (use a `useKeyboardOpen` hook). Direct, no magic.
- `supabase-js`'s `auth.getUser()` (no-arg) does NOT use the global `Authorization` header set on `createClient`. It uses GoTrueClient's internal session, which is empty on a fresh server-side client. Pass the JWT explicitly: `auth.getUser(jwt)`. Worth remembering for any Edge Function that gates on user identity via a forwarded JWT.
- `useColorScheme()` in React Native can briefly return the "wrong" value during view transitions on iOS — `'dark'` for one frame before settling to `'light'`. When a prop like `keyboardAppearance` depends on the scheme, this manifests as a visible flash. If the app supports only one mode today (or strongly prefers one), hardcode the prop instead of deriving from the hook. The conditional `scheme === 'dark' ? 'dark' : 'light'` is technically correct but isn't worth the flash.
- `keyboardAppearance` prop on `TextInput` is read from the bridged native config at the moment iOS decides to show the keyboard, which can race the React Native bridge by a frame or two with `autoFocus`. Even with `keyboardAppearance="light"` hardcoded, you can still see a brief dark flash if the app's `userInterfaceStyle` (in `app.json`) is `"automatic"` and the system mode is dark. Locking `userInterfaceStyle: "light"` at the app config level fixes this at the iOS UI-traits level, but it's a **native build-time setting** — JS hot reload won't pick it up. Requires `npx expo prebuild --clean && npx expo run:ios` or a fresh EAS dev build to land on the device.
- `LogBox.ignoreLogs(...)` only suppresses the visible red dev toast. It does NOT intercept the actual error or the cleanup path supabase-js takes afterward. So `ignoreLogs(['Invalid Refresh Token'])` is safe — it doesn't mask any state machinery, just quiets a noisy `console.error`. Don't be afraid of it when the underlying error is recoverable and the noise is dev-only.
- supabase-js does NOT auto-recover when the user referenced by the access token has been deleted server-side. The access token validates structurally and decodes locally fine; only the proxy's `auth.getUser(jwt)` call detects "User from sub claim in JWT does not exist". Auto-refresh fires only on token expiry, and by then the refresh token is also dead (it's tied to the same user) — so the cached session sits forever. The fix is to detect the proxy's 401 client-side and call `supabase.auth.signOut()` explicitly to clear the bad session. Same pattern would apply to any Edge Function that gates on `auth.uid()`.
- React state changes that depend on a child component's internal state need an explicit callback — there's no idiomatic way for a parent ScrollView to know that a child's `useEffect`-driven re-render produced new content. Exposing a callback like `onResultsRendered` from the child (fired from its own `useEffect` watching the relevant state) keeps the API minimal without leaking the child's internal state shape upward. Cleaner than lifting the state itself.
- `LayoutAnimation.configureNext({ duration: e.duration })` called inside a `keyboardWillShow`/`Hide` handler animates ANY layout change in the next render — not just the keyboard's KAV padding — over the same duration. Useful when you have a state-driven layout property (like a dynamic `paddingBottom`) that you want to ride the keyboard's animation. Without this, the state change snaps instantly while the keyboard slides smoothly, which reads as a jump.

**Bug fixes & lessons**
- Edge functions that throw an uncaught exception return Edge runtime's plain `"Internal Server Error"` text — not our structured JSON. Wrapping the entire handler in try/catch and returning the actual exception message in the response body turned an opaque "something failed" into a diagnosable `"unexpected end of file"` within one reload. Lesson applies to any Edge function we write later.
- The Supabase Edge runtime + chunked/compressed upstream responses is a known interaction-bug class. `Accept-Encoding: identity` on outbound `fetch` is the safe default for small JSON APIs.
- React Native's `Modal` always steals focus from any underlying input — even with `transparent` and `presentationStyle="overFullScreen"`. If you need an overlay that doesn't capture taps for an input that's already on the screen, use an absolutely-positioned `<View>`, not `Modal`. Modal is the wrong primitive when the user expects to keep typing into an input that's not inside the modal. Decision rule: if the keyboard needs to stay attached to a TextInput outside the overlay, use absolute positioning; if the overlay owns the TextInput, Modal is fine.
- Diagnosing focus/typing issues: insert numbered `console.log` probes at every event boundary (focus, change, effect, network) and ask the user to paste Metro output. Which log doesn't fire localises the failure faster than any amount of reasoning from the code alone. Worked twice this session — once for the TMDB proxy chunked-encoding error, once for the Modal focus conflict.
- Supabase database webhooks auto-fill `Authorization: Bearer <anon key>` and the default Edge Function gateway already verifies that JWT. Adding a custom `WEBHOOK_SECRET` check on top is redundant in the dashboard UI flow (the user would have to manually override the auto-filled header). For Edge Functions backing internal Supabase webhooks, lean on the gateway's anon-key check at MVP scale; add a shared secret only when you need to lock the function down even against leaked anon keys.
- Adding a new native capability (e.g. push notifications via `expo-notifications`) after the initial EAS dev build invalidates the cached provisioning profile — Apple needs to issue a new one with the right entitlement (here, `aps-environment`). `eas build --non-interactive` *cannot* do this regeneration because it requires Apple ID auth, which is a 2FA-gated interactive prompt. Hit this with the first push-notification dev build: build failed with "Provisioning profile doesn't support the Push Notifications capability." Fix is to run `eas credentials --platform ios` (interactive) to remove and regenerate the profile, or just re-run the build without `--non-interactive`. Worth remembering for any future native-capability addition (background fetch, in-app purchases, etc.).
- TypeScript module-rename gotcha: `use-profile.ts` returning `<ProfileContext.Provider>` JSX produces a wall of "TS1005: '>' expected" errors. Fix is to rename `.ts` → `.tsx` so the compiler parses the file as JSX. Worth checking when a hook starts wrapping children in a provider mid-refactor.
- `npx supabase gen types typescript --linked 2>&1 > database.types.ts` clobbers the file — the CLI's "Initialising login role…" status messages go to stderr but our `2>&1` merges them into the redirected stdout. Use `2>/dev/null > database.types.ts` (drop stderr) or `2>>/tmp/log > database.types.ts` (preserve stderr separately).
- supabase-js v2's `functions.invoke` JWT auto-attach is event-driven and racy right after `signInWithIdToken`. The `FunctionsClient` caches its `Authorization` header at construction (anon key) and updates it only when an internal `_handleTokenChanged` listener fires for `SIGNED_IN` / `TOKEN_REFRESHED`. If a function call lands between the sign-in completing and that listener propagating the new token, the FunctionsClient sends the anon key — which fails any Edge Function that calls `auth.getUser()` to validate the caller. **Lesson**: for Edge Functions that gate on user identity, always read the session and attach `Authorization: Bearer <access_token>` explicitly via `functions.invoke({ headers })`. Same call should still work if there's no session (header is `undefined`, function returns 401 — correct). One-line defence at the call site is cheaper than chasing flaky 401s.
- Substring profanity matching has the Scunthorpe problem out of the box: `'shit'` blocks `'shitake'`, `'piss'` blocks `'narcissist'`. Whole-word matching via `new RegExp('\\b(' + words.join('|') + ')\\b', 'i')` solves it. The regex is rebuilt per call, but for handle/display-name validation that fires on every keystroke the cost is below noise.

- **Real bug found — RLS without grants.** The title screen's status update was failing with Postgres `42501 permission denied for table items`. Root cause: our six schema migrations enabled RLS and wrote policies on every table but never granted the underlying table privileges to the `authenticated` role. Postgres applies grants AND RLS as two separate layers — without grants, every client mutation fails before RLS ever evaluates. The rls-auditor missed this across six migrations because its checklist only covered RLS, not grants.
